# 个人统一门户系统设计方案

我的建议是：不要只做一个传统的浏览器导航页，而是把它设计成一个「个人数字工作台（Personal Digital Workspace）」。

第一阶段，它是一个颜值高、打开速度快、桌面与手机通用的浏览器首页；第二阶段逐渐成为 LiteBox、OBsync、Linkwarden 等服务的统一控制入口；未来再考虑统一认证、共享组件、前端整合，甚至部分数据能力的收敛。

但有一个很重要的原则：

统一入口，不等于一开始就统一系统。

LiteBox、OBsync 目前各自的前端、后端、数据库都保留。新门户只负责导航、搜索、聚合信息和展示状态，不直接接管它们的业务逻辑。

我调研了 Homepage、Homarr、Dashy、Glance、Bonjourr、Sun-Panel 等项目。对你的需求，最值得借鉴的组合是：

- Bonjourr： 负责浏览器首页的视觉体验。
- Homarr： 负责自部署服务的卡片布局与交互。
- Homepage： 负责服务状态、API 数据和 Docker 集成思路。
- Glance： 负责信息流、动态小组件和多列布局。
- shadcn/ui + Motion： 作为未来自己开发个性化门户的 UI 基础。

其中 Homarr 已经有拖拽布局、应用集成、权限管理与 OIDC 支持，而 Homepage 对自部署服务的集成范围非常广。这两个尤其值得让 Claude Code 研究。

### 核心设计：不是一个页面放所有东西

我建议采用三个视图，但初期只有两个主要视图。

| 视图   | 目的         | 内容                          |
| ---- | ---------- | --------------------------- |
| 日常首页 | 浏览器默认入口    | 搜索框、时间、常用网站、快捷应用            |
| 应用中心 | 打开和管理自部署服务 | LiteBox、OBsync、Linkwarden 等 |
| 运行概览 | 了解重要服务情况   | 服务在线状态、异常提醒、到期信息            |

其中「日常首页」负责美观、轻量、高频使用，「应用中心」负责查找服务，「运行概览」负责少量重要状态。

不建议将完整的 LiteBox 监控界面复制到首页。 首页只展示异常数量或一个简短指标，深入操作仍然跳转 LiteBox。

页面的视觉重点：

- 卡片： 轻微玻璃质感、细描边、柔和阴影，不要过度透明。

我更倾向于这类 科技感 + 克制的高级感，不建议满屏的霓虹描边和持续运动的 3D 特效。

### 暂时不要做的部分

第一阶段不建议开发一个完整的插件市场、工作流自动化平台、统一数据库管理器、功能齐全的运维大屏，或者直接重构 LiteBox 和 OBsync。

## 五、现有自部署服务怎么接入？

这是整体设计中最重要的架构决策。

我建议所有服务采用统一的注册机制，定义三个集成等级：

L1：导航集成

只记录服务名称、图标、分类、访问地址和权限。这是所有服务默认支持的方式。

L2：状态集成

接入健康检查或只读 API，获取运行状态、任务数量、异常数量等。

L3：深度集成（以后再做）

在门户中嵌入部分业务组件、完成统一认证、实现跨系统操作。

### LiteBox 的接入方式

最开始只需要一个 LiteBox 卡片，点击后进入原来的 LiteBox 系统。

如果后续 LiteBox 提供合适的只读接口，门户便可展示例如节点总数、异常节点数、需要处理的告警数等汇总信息。

不要让门户直接查询 LiteBox 的数据库，也不必复制 LiteBox 的探针数据。

### OBsync 的接入方式

同样先是一个导航入口。未来如果 OBsync 具备任务状态查询 API，可以将最近一次同步结果、失败任务数量等展示在门户卡片上。

我目前没有核对 OBsync 的实际接口，因此这些属于建议的集成能力，不代表现有项目已经支持。

### Linkwarden 的接入方式

Linkwarden 更适合承担书签数据源角色：

门户的搜索框可以同时检索本地常用入口和 Linkwarden 收藏，但查询请求经由门户后端转发。API 密钥不应保存在浏览器端。

## 六、推荐技术架构

我倾向于让你从一个全新的、轻量级的门户项目开始，而不是直接将 Homarr 或 Homepage 改造成自己的业务平台。

原因是你对 UI 的个性化要求较高，并且未来可能深度集成自己的系统。直接 Fork 一个完整 Homelab 仪表盘，不一定比从小型门户开始更容易维护。

### 服务注册机制

建议为每个服务建立结构化的元数据，而不是把服务信息写死在 React 组件里。

例如：

```

{
  "id": "litebox",
  "name": "LiteBox",
  "category": "self-hosted",
  "icon": "server",
  "url": "https://litebox.example.com",
  "tags": ["node", "network"],
  "visibility": "private",
  "integrationLevel": "navigation",
  "enabled": true
}

```

之后再逐步扩展成支持不同访问地址、健康检查、权限控制、API 适配器的服务目录。

这套设计能够在将来收敛服务前端时保留原来的服务标识与入口配置。

## 七、Chrome 和 Safari 如何真正统一入口？

这个需求要特别处理，因为浏览器之间差异很大。

| 入口              | 第一阶段做法                 | 后续增强            |
| --------------- | ---------------------- | --------------- |
| Windows Chrome  | 设置启动页和主页为门户域名          | 自研新标签页扩展        |
| Windows Edge    | 设置启动页和主页               | 可兼容 Chromium 扩展 |
| iPhone Safari   | 收藏到 Safari 起始页，或添加到主屏幕 | 完善 PWA          |
| Android 浏览器     | 使用同一个 HTTPS 地址         | PWA 快捷入口        |
| 未来 macOS Safari | 书签、主页或起始页入口            | 按需求研究扩展         |

Chrome 的启动页、主页和新标签页并不是同一项设置。它原生允许设置自定义启动页、主页，但要完整替换新标签页，需要浏览器扩展。

## 八、安全与访问架构

因为这里会包含一些管理服务器和自部署服务的入口，我建议将安全策略作为基础能力。

最重要的是区分：

能看到服务入口，不代表拥有该服务的访问权限。

门户不应该持有所有后台的管理员密码，也不应该通过公开页面泄露内网管理地址。

建议第一阶段采取这些措施：

1. 使用独立 HTTPS 域名，如 `home.example.com`。
2. 私有服务目录和管理界面需要身份认证。
3. 入口支持公开 / 私有分级，避免对未认证用户展示敏感服务器信息。
4. 服务的访问地址可以区分内网、外网；实际能否访问由浏览器网络环境决定。
5. API 密钥仅存服务器端，并尽量采用只读、最小权限。
6. 运行状态定时在后端获取并缓存，避免首页加载时直接探测大量主机。
7. 不允许前端提交任意 URL 让后端直接请求，防止 SSRF。
8. 统一登录放在后续阶段，且只有支持 OIDC 等协议的服务才能真正实现 SSO。

对你而言，最适合的模式是门户用于集中发现服务，服务自身仍然保留独立认证和独立访问地址。

## 九、分阶段落地计划

阶段 0：UI 探索与设计确认

Claude Code 先研究参考项目，制作 2～3 套不同的桌面与移动端界面，分别偏沉浸式、科技控制台式和极简式。

交付：可运行的静态原型、桌面和手机截图、主题规范。不要开发业务后端。

阶段 1：门户 MVP

实现首页、搜索、快捷入口、应用中心、响应式布局、配置编辑、身份保护和 Docker 部署。

交付：可以正式作为 Chrome 主页和 iPhone Safari 快捷入口使用。

阶段 2：服务集成

接入 Linkwarden 搜索、LiteBox 运行摘要、OBsync 状态摘要，完善服务注册和只读适配器。

交付：统一服务目录和基础运行概览，不改变现有服务的业务代码结构。

阶段 3：长期整合

根据后续使用情况，评估统一认证、共享前端组件、跨应用操作和业务数据层的整合。

交付范围届时再定，避免提前设计过度。

让 Claude Code 开发时，我还会明确要求它对桌面 Chrome 和 iPhone Safari 分别做 Playwright 或真实浏览器验证；检查冷启动速度、布局溢出、键盘操作、接口失败后的降级表现，并确保门户不可用时，各服务原来的独立访问入口仍然可用。
